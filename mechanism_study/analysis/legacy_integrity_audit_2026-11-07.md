# 旧工具链修复后的只读复算

对应 Issue #2 任务 1。原目标是修复分支评分、续跑及审计的完整性缺陷；没有调用任何模型，也没有改写历史原始回答或历史评分表。

方法：同一个共享选择器供 scorer、branch_report、branch_pooled 和 runner 使用，按最早完成的完整成功分支选整组；核对首轮全文 SHA-256、完整首轮调用对象，以及复核实际重放的全文。重试不得逐程序混拼。解析失败或截断不按答案表现剔除或重试。详细规则与运行命令见 `../harness/INTEGRITY.md`。

结果：三目录选中 217、343、273 条程序记录，全部最终答案可解析。推理条件合计仍为 88/400 个唯一完整组，剩余 312 组。以上数字与此前只读审计一致；52 是分支尝试数，不能当作唯一组数。输入文件逐个 SHA-256 与固定提交 `cf8a5b64bb221882348c0091f401a0e1f4847d24` 的 Git blob 原始内容一致。完整分支清单、token 计量及输入哈希见同名 JSON。

花费：没有附可核验且适用于每次调用时段的价格表，三目录的货币总花费均为 NA；JSON 保留真实 usage 合计和缺失计数。不能从当前价格或历史报告中的概算反推精确实际花费。

验证：Python 3.12.13、SciPy 1.18.1 的任务专用环境中，36 项离线/mock 测试通过，包含跨进程锁争用、计划/题库/提示来源篡改及 5 项完整 CLI 报表情景测试。后者覆盖首轮全对、首轮全错、只有缺失证据题、复核结果全平局以及真实不一致对，确保零分母和无可检验差异时显示 NA，同时保留有数据支持的合法 p=1。所有修改入口及新增模块通过语法编译，`git diff --check` 通过。

真实历史数据的完整离线集成已执行：分别生成两个推理目录的 branch_report，再用 branch_pooled 合并，得到 88 个完整组、616 条程序记录；这批数据的关键证据在场首轮错误为 0，因此六种复核的修复率及全部修复比较显示 NA，不能解释为效果为零或方法等价。报表在临时验证目录生成，未覆盖历史报表；输入中的 36 个受 Git 跟踪的原始回答/原始评分文件全部与固定提交 SHA-256 相同，验证前后也未改变。完整校验信息和报表哈希见 JSON 的 `full_integration_validation`。

旧 H04 两个 CSV 的 400/560 行均通过原始记录与现评分规则逐列兼容校验；第一轮 H04 的 branch_report 可离线生成。这不等于重新完成全部历史 H04 合并推断审计。

PR #4 复审补充：在原修复提交 `813ebb3` 的临时 Mock 数据中，一手复现了两项遗漏：同长度但末字不同的 P1 仍可合并；plan 把 F01 重标为 F02 仍可评分。同目录语义代码/复核哈希冲突也能复现。现已用统一来源校验修复：评分、报表及续跑核对现存计划哈希；已验证语义源码、复核全文/长度和 raw 消息共同构成条件身份；题库原字节哈希、完整计划成员及 raw 首轮题面共同绑定 family/state/advice。无原始记录的计划组也不能被删除来缩小分母。单独修改 `runner.py` 哈希仍不构成拒绝理由。

兼容证据：历史大部分 case_files 哈希来自 CRLF 字节，当前 LF 文件可精确重建对应 SHA-256，审计逐文件记录此转换；不允许一般 JSON 重序列化或内容宽松匹配。第一批 H04 的旧 `procedures.py` 已重建为固定小型源码，完整 SHA-256 精确等于旧 manifest 的 `c88beeedef76b33356471108a520e1c51c7082880308fda04b4ddd49a85a2362`。缺少或无法匹配的语义源码明确拒绝，不假定它与当前条件一致。

旧计划的证据边界：原 manifest 没有 plan 哈希，raw 提示可验证案例/状态/建议/程序标签，manifest 可验证完整成员及重复次数，但不能独立恢复未进入提示的原 repeat/order 编号。当前固定历史审计另外逐字节核对了计划与 `cf8a5b6` 提交一致；不能把这项历史来源证明泛化到其他导入的旧运行。详细补充记录见 JSON 的 `pr4_provenance_review_validation`。
